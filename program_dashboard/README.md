# Delivery Pulse

One filterable page across projects and teams (PMN, CXCO, CXSUP, CXWFM, WFM, CXINT, INT): the release status in the
shape of the weekly release status email, plus bugs, customer-found bugs (CFB), epic dependencies and a capability
view. Every issue count links to the matching Jira issues, and every chart mark has hover text and a Jira link.

Layout, top to bottom: five headline tiles (Epics Delivered, Forecast Epics, EDCT Days, Open Bugs, Epics by AI,
each with a plain-fact line and a kicker saying whether it is the release, the last 30 days or today; Epics Delivered and Forecast Epics follow the Delivery Cycle filter and name the cycle in their kicker), a collapsible
**Needs Attention** panel, then **Delivery** (burnup), **Efficiency** (EDCT against the 10-day target; the average is shown from one epic, `n=` under each bar says how many epics it is) and
**AI Adoption** (share of epics built by AI agents) with a Week / Month / Quarter switch, **Quality** (open bugs
trend, customer-found bugs), **Dependencies** (open dependencies between epics on a board with a column per sprint), a separate **CXCROSS** section (status per project for each CXCROSS Capability, and which projects are behind), an **NFRs** section ("NFR Epics (Label or Category)", five tabs), a **Capabilities** section, then a separate **Delivery Cycle Governance** section (the pods of a program per delivery cycle; see below) and, last, "Release Analysis": trend by release, Done Capabilities per release, by project, by team
and data quality. **Section Strip**: the 11 section links (Needs Attention with its count in brackets when it is above zero, Delivery, Efficiency, AI Adoption, Quality, Dependencies, NFRs, CXCROSS, Capabilities, Cycles, Release Analysis) are a sticky strip directly under the Release headline, in one sticky stack with the filter bar (filter bar 20, strip 19, the Cycles Back bar 15; the stack is at most 30% of the window, otherwise the filter bar stops sticking first, and on a phone only the strip and the Back bar stick). It is 36 px tall (44 px with 14 px text on a phone, where it scrolls sideways inside itself, the next item peeking at the edge). A scrollspy (IntersectionObserver, no scroll handler) marks the section being read with ink text and a 3 px blue bar, `aria-current="location"`; Efficiency and AI Adoption, side by side above 1000 px, both show the bar; at the page bottom the last item is current; a click makes its target current at once and keeps it until the reader scrolls. A jump lands the section 8 px below the stack with the heading focused. Keyboard: one Tab stop (the current item), Left, Right, Home and End move between items, Enter jumps, Esc moves focus to the current section heading, and Alt + Down or Up goes to the next or previous section (not inside form controls); jumps are instant with reduced motion; in print the strip is static. A quiet floating "Back to Top" button appears when you scroll up after reading well down the page (it stays hidden if the page cannot scroll, near the top and while scrolling down). It sits at the bottom right, 16 px plus the safe-area inset from the edges, is 44 px on touch screens, and a click scrolls to the top and focuses the page heading (a harness test covers it). The header shows "Data as of ..." with a Refresh button and, compactly, the read time of each section with its own pull (Capabilities, the Open CFB Root Cause Analysis state). The charts group by resolution week, month or quarter; the EDCT Days and Epics by AI tiles do not follow the chart, they use the last 30 days (below). Both use the email's rules:
resolution day, AI-implemented epics for EDCT in Efficiency (Maintenance-category epics left out); the AI figures and Cycle Time per Release both leave out Maintenance and SOW.

```bash
set -a && source .env && set +a
python3 program_dashboard/build_dashboard.py              # read Jira (a few minutes) and render
python3 program_dashboard/build_dashboard.py --reuse      # re-render from the last pull, no Jira calls
python3 program_dashboard/build_dashboard.py --add-deps   # add dependency links (any issue type at the far end, plus story-level links under the release epics) and capabilities to the last pull (no changelog calls), then render
python3 program_dashboard/build_dashboard.py --add-planning  # also add due dates, target sprints, the sprint calendar, status-since dates, bug updates, the Flagged (blocked) field and the bugs under each epic
python3 program_dashboard/build_dashboard.py --add-hier      # add the CXCROSS Initiative > Capability hierarchy
python3 program_dashboard/build_dashboard.py --add-nfr       # flag the epics that carry the label NFR (the Issue Category is already in the data)
python3 program_dashboard/build_dashboard.py --add-bugs         # re-read the bugs (customer-found: reporter OR Salesforce case, Closed dates), the update dates and the Open CFB state, then render
python3 program_dashboard/build_dashboard.py --add-cfb-open     # root cause analysis state of the customer-found bugs (Open CFBs table), 4 requests
python3 program_dashboard/build_dashboard.py --add-capabilities # the Capability list and ALL their child epics, any project (Capabilities section, Done Capabilities per Release); a few minutes
python3 program_dashboard/build_dashboard.py --add-pods      # the pod labels of the epics (Delivery Cycle Governance, the pod level of the hierarchy); a full build and --add-planning include them
python3 program_dashboard/build_dashboard.py --add-cycles    # no longer does anything (kept so old command lines still run): the Confluence pods pull was removed
# The Atlassian site id for Refresh is read from the site (or from JIRA_CLOUD_ID); it is not stored in the repository.
```

Writes two files to `program_dashboard/build/` (git-ignored, they contain epic titles):

- `Delivery Pulse.html`: a single self-contained file (inline JS and SVG, no external libraries; the only external
  request is the Be Vietnam Pro font stylesheet, with Arial as fallback). Open it in a browser. Nothing is sent
  or published. The Refresh button there only explains that it needs the published page.
- `Delivery Pulse (artifact).html`: the same page as a fragment for the Artifact tool. Publish it with the `mcp`
  capability declared for the Atlassian connector and the single tool `searchJiraIssuesUsingJql`:
  `{"mcp": {"servers": [{"server": "Atlassian", "tools": ["searchJiraIssuesUsingJql"]}]}}`.

## Sandbox (check a change before it reaches the live dashboard)
The live dashboard is one published Artifact that many people open; the **Sandbox** is a second, separate Artifact ("Delivery Pulse Sandbox",
private to its owner until shared) that gets every change first.

- `python3 build_dashboard.py --reuse --sandbox` (or any other mode flag with `--sandbox`) writes `Delivery Pulse (sandbox).html` and
  `Delivery Pulse (sandbox artifact).html` and **leaves the two live files alone**, so a branch build cannot be published to the live page by
  mistake. The page is identical except for the tab title ("Delivery Pulse Sandbox") and a banner above it naming the branch, the commit
  (with "+ uncommitted changes" when the tree is dirty) and the build time.
- The flow: build the branch with `--sandbox`, publish the sandbox artifact file to the Sandbox URL (a new version each time), look at it,
  then merge the pull request and publish the normal build to the live URL. The Sandbox keeps the same `mcp` capability declaration as the live
  page, so Refresh from Jira can be tried there too.
- The Sandbox holds the same real data as the live page (it is built from the same payload), so share it only with people who may see the
  live dashboard.

## Time base
Every timestamp on the page is shown in Israel time (labelled), and the as-of day used for ages, sprints and SLAs is the
Israel-local date of the snapshot or of the last Refresh, whatever the viewer's timezone.

## Snapshot, and Refresh in the published page
Jira is read once at build time and baked into the file; the build time is shown at the top. The pull is slow
because cycle time needs one changelog request per Done epic and the burnup needs one per epic (about 3,000).

**Refresh from Jira** (the published artifact only) asks the viewer's own claude.ai Atlassian connector for what changed since the snapshot and
merges it in. The page also runs it **once, automatically, after the first paint** (button disabled with "Refreshing…", progress as "Updating live data: ...",
the filters stay usable) on **every open**: there is no 15-minute skip, so a reload never shows older data (the constant `LIVE_GUARD_MS = 0` in the template keeps the old guard switchable;
the time of the last Refresh without a failed step is still kept in `localStorage` as a per-viewer convenience, in try/catch, so the page works when storage is blocked). When Jira access is declined or there is no connector, the page keeps the snapshot and
says so calmly and persistently: "Showing the snapshot from <time>. Refresh needs Jira access." with a **Retry** button; there is exactly one automatic attempt per page load (it runs the **limited tier** only on the first open of the Israel day, see Keeping data fresh), and
manual retries are rate-limited. A local file has no connector and says "Snapshot from <time>".

What one Refresh reads, each step on its own (a failing step leaves **its own data unchanged**, says why in the result, and never blocks the others; nothing is applied half-way):
- **Epics and bugs**: new, moved, Removed and Done epics, new and fixed bugs, accessibility flags, the planning facts (due date, Target Sprint, parent Capability, Flagged, last update, NFR and pod labels). Read by `updated` in windows (one query for a recent snapshot, weeks for an old one, a window that reaches the 40-page limit is halved), so the page limit can not cut the read short.
- **Open CFBs**: the open set (dashboard projects, Bug, reporter = the CFB account OR Salesforce case, status not Done / Ready for Deploy / Closed / Resolved / Removed) is read again with the Root Cause Analysis fields; the CFBs that left it are read by key. The Root Cause Analysis state is classified in the page with the template **hashes** the build stored (no template text in the page). The Open CFBs table, the Open CFB Now counts, SLA, the Needs Attention rules and the links follow. A CFB that moved to Ready for Deploy leaves the list and is **not** counted as fixed until Done; one that moved to Done carries its Closed day and is counted by CFB Fixed.
- **Dependency links**: the links of every release epic changed since the snapshot are read again and the pairs that touch those epics are rebuilt as the collector builds them; an unknown far-end issue is read once.
- **Capabilities**: Capabilities of the dashboard projects and CXCROSS changed since the snapshot or in a release: status, fix versions, summary, and the epic-to-Capability parent. (A fix version moved after the snapshot, such as a Capability moved from 26.4 to 27.1, is picked up.) The Capability tables, the CXCROSS Required Fix Version and Behind counts, and Done Capabilities per Release follow.
- **Capitalization (every quarter)**: a **delta**, not a quarter re-read. Bugs, Stories and Tasks **in any status** that were `updated` since the snapshot are read; one that is Done with a Closed day on or after 2025-10-01 (Israel-local, resolution date when Closed is empty) is inserted or replaced, one that is no longer Done (reopened, Removed, ...) is deleted. A record the response did not return is never deleted: absence is not evidence (an empty response deletes nothing). An earlier-quarter issue that was flagged capitalized after the snapshot is therefore picked up. The chart caption says when it was last refreshed ("refreshed <time> Israel time", "not refreshed yet", or "not refreshed: <reason>; as of ..." when this step failed). It is a limited-tier step: it runs on the first open of each Israel day and the first two Refresh clicks.

**One header stamp**: "Data as of <date time> Israel time" is the **oldest of the live sources** (epics, bugs, open CFBs, dependency links, Capabilities; after a Refresh that is the time of the Refresh, a failed live step keeps its old time). The tooltip names the two limited sources (cycle time, Capitalization) when they differ from it, for example "Cycle time as of <time>; Capitalization not refreshed yet", and how many Refresh clicks are left today. The Efficiency, Release Analysis and Capitalization notes say when cycle time and Capitalization were last refreshed. The result of a Refresh is one plain sentence, for example
"Refreshed 2026-10-30 09:12: 120 epics and 85 bugs changed." A second sentence appears only when something needs action (a step that failed, an epic whose cycle time could not be read, a build older than 7 days). It stays under the button and in the stamp tooltip ("Updated from Jira <time>.").

**Refresh merges** into the existing record, it never rebuilds one from the response: it overwrites only what the response carries and leaves every other field as it was
(cycle time, sprint calendar, status-since, Closed and Ready to Deploy days and the reporter flags of a bug are kept). A field comes back empty (null) only when the response includes it as
empty; a field the response does not include is never cleared. A status change drops the status-since day of the old status, and a reopened epic drops its cycle time; the status-since day is filled in at the next build, the cycle time is read again by the next Refresh once the epic is Done.
**Cycle time (EDCT) of epics that closed after the build** is read during Refresh (limited tier): the step "Cycle time" asks the connector (`getJiraIssue`, `expand=changelog`) for each such epic's history and counts the days exactly as the collector does (`tests/dashboard_browser/harness.py::edct_in_the_page_equals_the_collectors_day_accounting` compares the two). It is applied only when every history was read in full; a step that fails leaves the epics as they were.

Story-level dependency links, the sprint calendar, and the Cycles pod configuration are read only when the data is built. Release join dates of new activity are the day Refresh saw it.

## Keeping data fresh
Refresh runs in **two tiers**. The page has no values that are never refreshed: everything comes from a live refresh; the limited tier is simply refreshed less often, so its oldest value can be about a day old.
- **Live tier** (every open of the published page and every Refresh click, in this order): epics, bugs and accessibility bugs first (access errors surface here), then open CFBs, dependency links, Capabilities.
- **Limited tier** (after the live steps): the cycle time of newly Done epics, then Capitalization (all quarters). It runs on the **first open of each Israel-local day** (this does not use a click) and on the **first two Refresh clicks of the day**; after that a click runs the live tier only and says so ("Cycle time and Capitalization were not refreshed: they update on the first two Refresh clicks each day, and those are used. They update again after midnight, Israel time."). The constants are `SLOW_AUTO = 1` (0 would make an open run the live tier only) and `SLOW_CLICKS = 2` in the template. The allowance is per viewer and day, kept in the viewer's browser (`localStorage` key `dp.slowRuns` = `{day, n, auto}`); it is a **courtesy, not an access control**: clearing storage or changing the clock resets it, and with storage blocked it is counted in memory for the page load. It is reserved right after the epics and bugs step succeeds and is **not refunded** when a limited step then fails (a refund would make an unbounded retry loop); a run counts for the day it started on. A refresh that fails at its first step, and an automatic refresh that is skipped, use nothing.
- **Kept for a reload**: what the limited tier last read is stored in the viewer's browser (`dp.slowData`: the cycle times it read, Capitalization with its refresh time) for **this data version**, so a reload shows the last limited refresh (up to about a day old) without asking Jira again; a different data version (another build or data layout) discards it, a stored value never replaces a value the data already has and never makes data look newer than it is, and a storage problem is skipped silently.
- **Build-only**: story-level dependency links, the sprint calendar, and the Cycles pod configuration. A rebuild is the only way to get them, so schedule one: the full pull is slow (one changelog request per Done epic), so run `build_dashboard.py` on a schedule (nightly is enough, because the page refreshes itself on open) and publish the result.
- **Scheduling**: never at the top of the hour (GitHub Actions cron runs scheduled at :00 land 1.5 to 3.5 hours late); choose an odd minute such as :17 or :43. A green job is not proof: **verify that the trigger fired** (the run list shows a run for today's date, and the stamp on the published page moved) rather than only that the last job passed.
- If the page shows "Showing the snapshot from <time>", the viewer has not allowed Jira access or the connector is not connected; **Retry** asks again.

## Filters
Release (bare numbers; a release that is running gets an "In Progress" chip), Projects, Teams and Delivery Cycle (**both
cycles by default**). Reset Filters counts every changed control. Section-level controls: Week / Month / Quarter for the
EDCT and AI charts, Priority, CFB All/Yes/No and Accessibility Bugs All/Yes/No for the Bugs Backlog, Version / Quarter / Month for the
CFB chart and table, and **Commitment Level** (checkbox chips, Capabilities section only, described under Capabilities below).

**Projects** is a segmented control (`All Projects | PMN | CXCO | CXSUP | CXWFM | WFM | CXINT | INT`) plus a **Multi-Select** toggle
(tooltip: "Select several projects: click chips to add or remove them. Shift-click does the same."; a first-use hint, "Click projects
to add or remove", goes once a project has been added or removed). *Single* mode (the default): a click on a project selects only that
project, All Projects selects all seven, the arrow keys move and select (one Tab stop, roving tabindex; Space and Enter select);
Shift, Cmd or Ctrl-click adds or removes a project and switches to multi-select mode. *Multi-select* mode: a click toggles a project,
the last project cannot be removed (the status line says "At least one project must stay selected"), the arrow keys only move, Space and
Enter toggle. The mode is derived and never stored: two to five projects always open in multi-select mode, the button reads
"Multi-Select (2 of 7)" then and cannot be left until one project or all are selected. There is no empty selection by any route.
Every change is announced politely ("Showing PMN only, 19 epics delivered", the Epics Delivered tile). There is no summary line under the filter bar any more: the filter chips and the "Reset Filters (n)" count show what is changed.
**Teams** keeps the searchable multi-select; "All Teams" is the first row and every row has an **Only** action (shown on hover,
focus and on touch screens). **Delivery Cycle** is a single-choice segmented control (a radio group, the same look as Accessibility Bugs and Group CFB By) with three options, **Both cycles** (the default) | **Cycle 1** | **Cycle 2**, where Commitment Type was: one click selects exactly the option it names, the selected one is filled blue with a check, and a line under the control says what is shown ("Showing Cycle 1: W1 to W6", "Showing both cycles: W1 to W12"). It changes the Delivery burnup, the Cycles section and the Epics Delivered and Forecast Epics tiles only (see *Delivery Cycle filter*). The Commitment Type filter was removed: every epic counts whatever its Commitment Type, which is what the page always did by default. On a phone the
chips are 44px tall and Multi-Select takes its own row.

In a file the filter state is kept in the URL hash, so a view can be shared as a link, e.g.
`#r=26.4&p=PMN&t=Team%20Alpha&dc=2`: `r` release, `p` projects, `t` teams, `dc` delivery cycles (`dc=1` or `dc=2`,
omitted for Both cycles, the default; older links of the two-checkbox control open the same way), `ax=all|yes` Accessibility Bugs All or Yes (omitted for No, the default; an older `ax=1` link opens as All), `bp` bug priorities, `cfb=yes|no`, `g=week|quarter`
(EDCT and AI period), `cg=month|quarter` (CFB grouping), `dp=<relationship>|<flag>|...` (dependency board quick filter: one relationship of `all` (the default, omitted), `epics` (Internal), `external`, `blocking`, `cx`, written first, then any of the flags `overdue`, `unplanned`, `gap`; an old single value such as `dp=overdue` or `dp=epics` still reads), `cx=committed|notset|stretch` (CXCROSS Commitment Type radio, All by default), `nt` (NFR tab); `p` is written in the canonical project order (PMN, CXCO, CXSUP, CXWFM, WFM, CXINT, INT) whatever order the chips were clicked in; there is no empty selection, and an older link with `p=none` reads as all projects, and an older link with `c=...` (the removed Commitment Type filter) is ignored. In the published page the filters are remembered in the
viewer's browser instead. A section whose filters leave nothing to show says why.

## Definitions
Taken from the Program Intelligence Agent (`.claude/agents/program-intelligence-agent.md` and
`program_intelligence/definitions/*.yaml` on branch `claude/zealous-cannon-ls64p7`). They are restated in
`build_dashboard.py` and the template, so this tool does not need that branch at run time.

- **Removed is excluded from every figure.** Done means the status named Done, never Jira's Done category.
- **Scope is Fix Version plus Commitment Type** (customfield_10094). Status never defines scope.
- **The scope target** is always Committed or no Commitment
  Type, with Stretch left out. **Forecast Epics is the target scope on the first day of W1** (the epics that were
  in the release on that day and still are); the burnup's scope label, point, tooltip, subtitle and caption and the
  even-pace reference read the same single value, and the tile adds how many were added since (and today's count,
  as a link). Before W1 it shows the target so far. The links use `fixVersion WAS "<release>" ON "<W1 date>"`.
  The Epics Delivered tile counts Done epics of any Commitment Type (its tooltip says so); its fact line says "of 829 target scope", and the number's tooltip adds how far the Done count is ahead of or behind the even-pace reference ("6 ahead of even pace on day 12 of 84; a reference, not a forecast").
  **These two tiles follow the Delivery Cycle filter** (the other three never do; see *Delivery Cycle filter*): `deliveryTiles()` in the template, which reads `dcState`, `dcDomain` and `w6Model` (the burnup's own helpers, nothing is derived again). The numbers are the whole release's in every view; the cycle changes only the target the tile compares with, and the kicker says which cycle ("Release 27.1 · Delivery Cycle 1"), so the cycle is never shown by colour alone. **Both cycles ticked** (or a release with no cycles): the tiles exactly as described above. **Cycle 1 only**: Epics Delivered is the same Done number, its line reads "of N planned by the end of W6" (N the Committed epics planned by the end of W6, the burnup's dotted marker) and its fact line "Delivery Cycle 1: W1 to W6" ("starts (W1 date)" before W1, "ended (date)" once W6 is over); Forecast Epics shows N with "Planned by the end of W6, Delivery Cycle 1 ends (date)". **No release scope appears in this view**. N is a link to the query `w6Model` builds (Jira recalculates it; plain text over the 6,000 character budget); with N = 0 the tiles say "no epics planned by the end of W6" and N is plain "0". **Cycle 2 only**: Epics Delivered is the same Done number of the release scope ("of 120 target scope") with "Delivery Cycle 2: W7 to W12" (", starts (date)" before W7); Forecast Epics is the release scope tile unchanged, with its "+N since W1" line. In the two cycle views the number's hover reads "N epics Done in 27.1, any Commitment Type" and "Whole release, cumulative since its start; Delivery Cycle 1 changes only the target." (the even-pace comparison is left out: the burnup measures it to the end of the cycle's window, a different reference from the whole-release one the hover names). Oracle: `tests/dashboard_browser/tile_oracle.py`.
- **EDCT Days and Epics by AI tiles = the last 30 days**, not the calendar month (a month-to-date tile was nearly empty in the first days of a month: "only 0 epics, need 5"). The kicker says "Last 30 Days". The window is the 30 days ending on the as-of day (the page's own "today": the data's refresh day in Israel-local days, the same day base as every resolution date), inclusive: `resolutiondate >= "<as-of minus 29 days>" AND resolutiondate < "<as-of plus 1 day>"`. Example: as of 2026-11-01 the window is 2026-10-03 to 2026-11-01. The comparison under Epics by AI is **Previous 30 days** (the 30 days before the window, as-of minus 59 days up to the window start, no overlap, no gap), with its dates and counts in the hover. The same bounds drive the numbers and every Jira link of the two tiles (calculated queries, no key lists), so a link opens exactly the epics counted. Populations are unchanged: EDCT Days averages the AI-implemented epics with an EDCT (Maintenance out); Epics by AI is the AI share of the resolved epics (Maintenance and SOW out). **The EDCT average has no minimum: one epic is enough** (owner decision; `EDCT_MIN_N` = 1, the same constant drives the tile, its target line and the Efficiency chart, so the tile and the chart never disagree for the same epics). A window with no AI-implemented epic that has an EDCT shows "–" and "no AI-implemented epics with an EDCT"; Epics by AI keeps its 5-epic rule ("too few for a share"). The charts of Efficiency and AI Adoption (and their headline numbers, per-period tables and links) stay on calendar weeks, months and quarters, so their current period is not the tile: "2026-10 so far" and "Last 30 Days" are different windows. Window code: `lastDays()` in the template; the oracle is `tests/dashboard_browser/tile_oracle.py`.
- **Epics by AI** counts Done epics resolved in the last 30 days (the window above), **leaving out the Issue Categories Maintenance and SOW** (see the next paragraph), that carry a release fix version from the first to the last listed release (the Jira links carry the same filter, so they open what is counted); the tile also shows the epics **not marked as AI** as its own link: the field is a multi-select, so "not Yes" is `(cf[15229] is EMPTY OR (cf[15229] = No AND cf[15229] != Yes))` (an epic ticked both Yes and No counts as AI); Yes plus not-AI always equals the resolved count. Never `!= Yes` alone: it drops the empty ones. In the AI Adoption chart every bar opens the epics of its period (the bar's own population) that are **not** marked as AI; the hover text says so ("2026-09: 85% marked as AI (242 of 284). Click opens the 42 epics not marked as AI"), and the View Data table links the resolved, marked and not-marked counts of each period.
  **AI exclusion (Maintenance and SOW).** Epics whose Issue Category (Jira field cf10139, stored spelling, compared without regard to case) is Maintenance or SOW are left out of **every AI figure**: the Epics by AI tile and its previous-30-days line, the AI Adoption chart for Week, Month and Quarter, its View Data table, the Release Analysis AI share (the Epics by AI tile for the release, the AI chart per release and the Epics by AI column of its table) and all their Jira links, which carry `(cf[10139] is EMPTY OR cf[10139] not in (Maintenance, SOW))` next to the same resolved-in-period and fix-version population as the denominator. One constant in the page (`AI_EXCLUDED_CATEGORIES`) drives both the numbers and every link. It is shown, not hidden: the tile and the section subtitle say "Maintenance and SOW epics are excluded from every AI figure" with the number of epics left out in the displayed period or population as a link (`cf[10139] in (Maintenance, SOW)`, same basis); the AI View Data table has an "Excluded (Maintenance, SOW)" column per period with links, the release table has the same per release, and "How this is calculated" explains why. **EDCT is not an AI figure.** Efficiency keeps its own rule (AI-implemented epics only, Maintenance only out, as the weekly email counts it; its values and links are unchanged, its query text is its own constant `EFFICIENCY_KEPT_JQL`). Cycle Time per Release shares this same list, see "Done-based figures per release". The URL state of the tile does not change.
- **Cycle time** is EDCT only: calendar days an epic ended in In Progress or Validation, flagged days excluded.
  Identical to `dashboards/edct_from_jira.py`; the build checks every epic against it and reports differences. Trend by Release shows P50 and **P90** (linear interpolation) for releases with 5 or more Done epics that have an EDCT and are not in the Maintenance or SOW Issue Category (the Cycle Time per Release rule, see "Done-based figures per release").
- **Burnup** (selected release): only the 12 delivery weeks W1 to W12, from the first day of the second week of
  the Jira release window (the IP week is not drawn) to the release date. Scope is one number, the target-type
  epics in the release on the first day of W1. Done is every epic closed in the release, **whatever its Commitment Type** (a Done Stretch epic is still delivered; the same Done as the Epics Delivered tile), cumulative by resolution
  date, with earlier closures counted at the start and later ones on the last day. The dashed line is an even pace
  from zero to that scope, a reference and not a forecast. A dotted marker and a fact line under the chart present the first six weeks (W1 to W6, ending on W1 start + 41 days) as **Delivery Cycle 1**: the number of **Committed** epics planned in it (strictly Commitment Type Committed, Not Set excluded), out of all Committed epics in the release, Done and not Done, and those with no due date or Target Sprint. An epic is planned in the cycle when its Target Sprint (counted by its end date, so the 2nd sprint of the release or earlier) or its due date is on or before the cycle end; **with both, the later one counts**, otherwise the one that exists. The dependency board keeps the due date over the Target Sprint. The Jira links reproduce the same set. **The count is printed on the chart**, left of the dotted marker at the top of the plot: "Delivery Cycle 1 · N epics planned" with "N Done" under it (the same N and Done as the fact line below, always in sync; the label wraps to three or five short lines when the space left of the marker is narrow, so it never touches the axis or the other chart labels). A dot on the marker sits at N on the chart's own epic scale (a fact about the plan, not a forecast). - **Tooltip standard (hover text on a number, bar, flag or label)**: one pattern, written where the number is built (`tlink`, `ga`, `tipFocus`, `tipAttr`), never read back from another element's text. Line 1 (shown bold) is the number, what it counts and the scope, at most 12 words; line 2 is one of what is left out, the basis or a comparison, at most 15 words; line 3 only when the list the link opens differs from the number ("Opens the 12 epics not marked as AI." or the exact-list line). Budget: the first block (the first two lines) at most 25 words, at most 4 lines; the exceptions are a key-value readout (the burnup day), a line that carries a data list (the exempt Issue Categories), a list preview (Needs Attention chips: a header, at most three items, one action line) and a line that a test asserts word for word. The rules: R1 lead with the number, what it counts and the scope; R2 one block, then stop; R3 do not repeat the visible text of the element; R4 a link line only when the list differs from the number; R5 a definition that sits in How this is calculated is not repeated in a hover (a hover that must define a term uses `Term: definition.`); R6 one shared text per concept, written once in code (`TB.tip` for the target scope, `EXACT_NOTE` for an exact list, `CY_POD_LIMIT`, `AI_EXCL_WHY`); R7 one term per concept (running, In-Progress, as-of date, Done end, planned date, CFB; a running release is always "(running)", never "(in progress)", "Provisional" or a bare asterisk); R8 no instruction about another element ("hover or focus the flag", "the number above opens them"); R9 reachable on keyboard focus and read the same by a screen reader (`tipFocus`, never a bare `title` for essential text); R10 build the text where the number is built. Every counted noun after a number goes through `nn(n, "epic", "epics")`, so a count of 1 never prints "1 epics". The exact-list line is `EXACT_NOTE(m)`, a function of the number of issues the link names (`keyCount`); a link that names Capabilities and opens their epics says so (`parentNote`) instead, because its key count is not the number it shows. ## Usage statistics

The published page counts how it is used, so the owner can see how many people use it, how often they come back, which sections they read and which controls they use. It is a self-contained block at the end of the template script
(`USAGE_VOC`, `USAGE`); nothing above it knows about it. It wraps `saveState` to see which controls changed, and two small hooks tell it what the page itself knows: `refresh()` reports how a Refresh run ended (`refresh.result`, read in its `finally`) and the Section Strip says whether the reader is above its first anchor (`SEC.top()`).
A local copy, a page without the capabilities and a viewer without an id record nothing and show nothing.

**Privacy.** The record is **pseudonymous, not anonymous**: it is keyed by an opaque user id (a `u_...` code), the editors of the page can read every record, and an id that is stable for a person is still a way to follow that person over time. Names and e-mail addresses are not recorded: the page reads only `user.id()` and declares `user` **without scopes**.
Never recorded: names, e-mails, issue keys, team, pod or project names (the project chips are configuration the viewer chose: only the number of selected projects is kept), the release looked at, search text, the address of a Jira link, the browser, language, referrer or address, free text of any kind.
Every recorded key comes from the fixed lists below; anything else is dropped. A visible note at the very bottom of the page, shown only after the first successful write of a visit, says what is counted (the wording is in the template: "per pseudonymous user id (a code, no name or e-mail; only the owner and the editors of this page can read these records)")
and ends with the retention sentence ("Kept for 12 weeks: older weeks are removed from your record when you next open the page, and the owner also deletes records not seen for 12 weeks"). A viewer whose write is refused (a view-only viewer) never sees it, and it disappears if the visit stops recording.

**Publish with these capabilities** (the access rules are declared at publish time, not in the page; they are also written in the template comment):

```json
{"db": {"rules": [{"path": "", "write": "admin"}, {"path": "usage", "read": "admin", "write": "admin"}, {"path": "usage/{self}", "read": "interact", "write": "interact"}]}, "user": {}}
```

Each person writes and reads only their own record `usage/<id>`; Editors and the owner read all (the owner grants Editor access in the Share menu, and that is what lets a person see the Usage view). A viewer at the `view` level can never write: their visit records nothing, silently.

**Live usage view (owner and Editors).** The block at the very end of the template (`UV`) gives the artifact's owner and anyone with Editor access the whole usage report inside the page: a "Usage" link at the right end of the Section Strip (shown to them only) opens a closed "Usage" section with Show usage / Refresh usage buttons; it reads the collection `usage` when opened and on each Refresh (a list, never a write) and draws the same page `usage_report.py --show-all` makes (key figures with trends, people per week and day, section, control and device reach, the day-and-hour map, whether people come back, recording health, how it is measured), with no ids. The report is computed in the browser by `usage_view/*.js`, a literal port of `usage_report.py` (same names, same output, one file per part: `core.js`, `signals.js`, `views.js`, `render_a.js`, `render_b.js`; the rules are in `usage_view/PORTING.md`), joined by `usage_bundle.py` and inlined by the build at the `/*__USAGE_REPORT_JS__*/` line of the template (with the build's release and sprint calendar); the page is drawn in a shadow root so the report's own style sheet and the dashboard's do not touch each other. Because the port is literal the Python report is its oracle: `tests/dashboard_browser/usage_port_check.py` runs it in headless Chrome on fictitious exports and requires the model, every number, every page block and the whole page to be byte-for-byte equal, also for exports that make every signal fire and for random ones (`usage_port/port_check.py` prints the first differences when it is not). Change the report in `usage_report.py`, then in the port, and let that suite say whether they agree. The page hides the view from everybody else, but what really protects the records is the rule above (`usage` read and write at Editor level), so the database itself refuses a read by anyone below Editor.

**The record** (schema 2), one document per person (never one per event or per visit; the database holds at most 25,000 documents). A session is one visit; a field a v1 session lacks means *unknown*, never 0:

```
usage/<id> = {u, v: 2, first, last, pr?,                  // id, schema, first and last Israel day; pr = 1 when the size cap has dropped weeks
  w: {"S<date>": {"<Israel day>": {"<visit id>": {          // the work week Sunday to Saturday keyed by the date of its Sunday (a v1 key "2026-W44" is still read); a visit id is 8 random characters
    t,            // opened at, in HOURS since the epoch (v1: minutes)
    s,            // active seconds: the page in front, focused, and input in the last 60 s, counted every 5 s
    vs,           // visible seconds: the page in front, focused or not (a frame may report no focus: s can then under-count readers who only scroll)
    g,            // 1 = a glance: visible 5 s or more, no input, under 30 s visible (written when the page was hidden or left); left out otherwise
    sec: {<section>: seconds}, nav: {<section>: clicks on the strip and the skip links},
    f: {<control>: changes}, l: {<section>: Jira link clicks (left or middle button)}, o: {<disclosure>: opens},
    r: Refresh presses, rs: Reset Filters presses, rr: 1 = Reset Filters pressed after at least one control change in the same visit,
    ro: {ok, fail, declined: outcomes of Refresh runs the reader started}, rt: presses of the Retry link,
    lv: 0 live | 1 snapshot only (no connector, or Jira access declined) | 2 live with a failed step (the last Refresh run of the visit; left out until one has ended),
    fa: age of the data on screen at the start of the visit: 0 under 1 h | 1 under 24 h | 2 under 72 h | 3 older,

**Rules of counting.**
- Reading time: every 5 s tick in which the page is visible, focused and was used in the last 60 s adds 5 s to `s` and to **every section of the current row of the Section Strip** (the current item and the ones lit beside it when sections stand side by side, for example Efficiency and AI Adoption), or to `top` before the first anchor has been passed. So the `sec` values of one visit can add up to more than `s`; each one is at most `s`. Seconds with no section in front are not recorded.
- A control change is counted from the address keys the page writes after every state change (compared with the last state), only when the reader acted in the last 2 seconds, and Reset Filters counts as Reset only. A disclosure counts only when the reader opened it (a click on its summary), not when the page redraws it open. A Jira link counts on a left click and on a middle click (`auxclick`, button 1); a right click is not counted.
- Errors: an uncaught script error or an unhandled promise rejection is `er`; a browser notice that is not a fault of the page (a message starting "ResizeObserver loop") is `erb`, counted apart and never to be flagged. Neither message is kept.
- Refresh: `r` counts presses of the Refresh button, `rt` presses of the Retry link of the automatic attempt, `ro` how the runs the reader started ended (`ok` every step succeeded; `fail` a step or the read failed for another reason than access; `declined` the Atlassian connector is missing or Jira access was not allowed). The automatic run on every open is not counted in `ro`; it sets `lv`.
  `lv` is the outcome of the latest run of the visit: 0 after `ok`, 1 after `declined`, 2 after `fail` (including a total failure that is not an access problem, because the data on screen is then the snapshot with a failed read). `fa` and `lf` are taken when the visit starts (`fa` from the stamp the header shows, the oldest of the live sources, before the automatic Refresh has run).
- A visit is a run of use. **A new visit (a new session id) starts after 30 minutes without input and at Israel midnight**; the finished visit is written first. A visit that stays open across midnight with a reader still active is split at the next 5 s tick, a visit with no one at the page at the next input.
- **A glance counts.** A visit that was visible for 5 s or more (one 5 s tick) with no input and under 30 s visible is recorded when the page is hidden or left (`visibilitychange` to hidden, `pagehide`; best effort) with `g: 1`, `s: 0` and no counters. Looking at the page again afterwards is a new visit. A visit visible for 30 s with no input is written after those 30 s as before (no `g`).
- Not counted: pointer movement as input (it keeps a visit alive but is not a click, key, scroll, touch or change), time while the page is hidden, a visit under 5 s with no input.

**When it writes.** Never at page load: the first write follows the first real input, 30 s of visible time for a visit that only reads, or the end of a glance (page hidden or left); then at most one write every 30 s while the page is visible and something changed, and when the page is hidden or left (best effort). Nothing is written from an event handler except on those hide/leave events.
One write at a time. The first write of a page load reads the record (`get`) and creates it (`set`) or merges into it (`update`); it prunes weeks older than 12 (the cut is the Sunday 11 weeks before the current one; a week of schema 1 is kept while its Sunday is not before that), keeps at most 10 visits a day (a day with more than 20 triggers the clean-up; a page load never creates more than the 10 the day allows) and keeps the record below 90 KiB, rewriting with `set` only when something has to go; when the size cap drops weeks the record carries `pr: 1`.
After that every write is an `update` of the visit's own object (with `v: 2` and `last`), so a re-sent write is harmless and several tabs do not overwrite each other. A finished visit (a split) is written before the new one.
`unavailable` is retried once after a short random pause; after 3 failed writes in a row, or a refusal that cannot succeed (`invalid_argument` for a view-only viewer, `quota_exceeded`, `revoked`), the visit stops recording and the note disappears. A failure never reaches the page: a refused viewer is never asked twice.
**Retention.** The page removes weeks older than 12 from a person's record the next time that person opens the page and a visit is recorded; for a person who stops coming that never happens, so the owner also deletes records not seen for 12 weeks (the report counts them).
**Size.** A session costs about 290 bytes in a realistic visit: the heavy but realistic pattern (5 days a week, 3 visits a day, 12 weeks, 181 sessions) is about 51 KiB, under the 90 KiB budget; at the absolute maximum (every day, 10 full visits a day) the 90 KiB limit drops the oldest weeks first, so fewer than 12 weeks are kept (one week at that extreme, about 65 KiB, with `pr: 1`).
**What is and is not counted.** Only people who open the published page, can write to the database and have an id; the person's own visits, the owner's and testers' included. Signed-out viewers, view-only access, offline copies, browsers that block storage and visits that end before 5 s with no input are not counted.
Not verified in a headless file build: how the real `db` and its consent prompt (if any) behave, and whether `document.hasFocus()` is true inside the published frame; the tests use a fake store with the documented semantics (`tests/dashboard_browser/usage_oracle.py`). `vs` against `s` shows it: a visit with `vs` > 0, input (`nav`, `f`, `l`, `o` or `r`) and `s` = 0 is a focus problem.

python3 program_dashboard/usage_report.py --demo --html usage_demo.html --standalone      # fictitious data, "Demo data" banner, opens as a file
python3 program_dashboard/usage_report.py export.json --html usage.html --as-of ... --min-group 1   # a page for the owner alone: every number is shown as it is
python3 program_dashboard/usage_report.py export.json --html usage.html --as-of ... --show-all    # owner page with no minimums on what is drawn (see below)
```

`--as-of` is when the export was taken (without it the report reads the export as taken today and says no export time was given: the last day in the data is never taken for today; an export older than 3 days is warned about). `--since` is the go-live day (the Sandbox before it is ignored and
the weeks before it read "before the data starts"). `--audience N` is optional: without it the page says the audience size is not supplied and shows no adoption percentage; with it the page says "x of an audience of N" and that it is a lower bound. `--min-group N` (or the `min_group` threshold) is the smallest group of distinct people the report shows a number for; **the default is 5**, because a count of 1 to 4 people can point at a person and the page can be shared, screenshotted or pasted into a deck.
`--show-all` removes the minimums on what is drawn: every group size (min group 1), percentages for any denominator, the day-and-hour map from one engaged visit, and the week in progress (to date) in the views that otherwise need a completed week (section and control reach, devices, freshness, the page version). The statistical verdicts that compare weeks (growth, change signals, simplify candidates, habit, who comes back) keep their own rules, because they cannot be computed from fewer weeks. A thresholds file still overrides it. Keep the page private: with few people the numbers describe individual visits.
With a smaller N the report shows the numbers of smaller groups: `--min-group 3` withholds groups of 1 and 2 and prints `<3 users`, `--min-group 1` withholds nothing and the partition rule (a figure that would reveal a withheld group by subtraction) is inert. Every guard, chart, stub, scorecard and sentence follows the setting, and the coverage ribbon and "How this is measured" state it
("Groups under 5 people show <5 users"; with 1: "Small groups are shown as they are: with few people these numbers describe individual visits, so keep this page private and do not share screenshots of it"). It moves only the privacy guard: a percentage still needs a denominator of 20 (else counts with n=), a baseline 5 completed weeks, a weak signal is under 30 active people and a growth verdict needs 6 completed weeks.
`--thresholds file.json` overrides the
`THRESHOLDS` dict at the top of `usage_report.py` (every threshold has one name there). `--calendar` adds the release milestones, the sprint boundaries and, if the owner adds them, `events` (review days) and `quiet_weeks` (dates inside weeks to leave out of every baseline).

The record this report reads is defined in one place, `RECORD_SHAPE` in `usage_report.py` (schema v2; schema v1 records are read too, and a field a v1 session lacks is Unknown, never 0). The report reads the user id only to drop a duplicated document and never prints it. A record is **pseudonymous, not anonymous**: the id is a code with no name
or e-mail, but the editors of the published page can read it. The exported JSON file is deleted after the report is built, and a screenshot of the page carries the same rules as the page.

**What the page shows**, graph first and in the order of an analytics report (the style of Google Analytics reports): a coverage ribbon (two lines: who is counted and who is not, pseudonymous and not anonymous, `<5 users`, never used to rank); **Key figures**, five scorecards of the same anatomy (title, one big value, a one-line sub with the number behind it, the change against the week before in an arrow and words, a sparkline of the weeks since the last change of the recording rules): people active (the hero, with its usual range), new people, engaged visits per person, median visit length and **Device** (twice as wide as the others, with a donut of the split and its legend beside it; the glance share is under Recording health and in the text report)
(the largest window-width class with its share, "Desktop 50%", and in the sub line the others and the number of visits, "Phone 50% · Tablet 0% · 2 visits"; the percentages always show, however small the base, add up to 100 (largest remainder) and carry their n; a class under the minimum group size prints the guard text and is a hatched arc of a fixed size. The card is twice as wide as the others and holds an inline-SVG donut (at least 110 px) with a legend beside it, "Desktop 50% (1 of 2)", the number of visits in the centre and the percentage on every segment of 12% or more; every visit counts, glance or engaged; the page records the width class `d`: narrow up to 480 px = phone, medium up to 900 px = tablet, wider = desktop; the caveat is printed under the heading: by browser window width, not device type, a narrow desktop window counts as phone; the table is under Show data and the text report prints the same card).
A scorecard **always shows its value for the data to date**: the last completed week when it can be compared, otherwise everything recorded so far, marked "so far" with its period (for example "so far, 1 Nov to 2 Nov (week in progress)"); only the comparison part (the arrow and change, the usual range, the sparkline) falls back to a short muted note ("No comparison yet: first week of data") and one line under the heading says why and when comparisons start (data that starts mid-week leaves that week uncompared; a change needs two complete weeks). A partial period is never compared with complete weeks, and "Is adoption growing?" stays "too early" until 6 completed weeks.
A figure that truly cannot be shown (a group under the minimum, nothing recorded, "Recording rules changed" only when an earlier week was recorded under the old rules) says so in a few words over a muted skeleton; **Trend**: people active per week (a line for the complete weeks, hatched columns for the incomplete ones, the usual range, the calendar events W1 starts, Delivery Cycle 1 ends and Release ends, the change of recording rules, and the growth verdict:
"too early" is a first-class answer, growth needs 6 completed weeks, +20% and +3 people) and people active per day for 28 days; **What people read and use**: section reach and control reach as horizontal bars (page order, never ranked, a guarded row is a hatched stub with `<5 users`), what people do (shares of people or of visits, each row names its base),
and stacked bars for screen size, page version and the freshness of the data; **When people visit**: engaged visits by weekday and hour of the day (Israel time; a cell of fewer than 5 people is hatched; shown from 50 visits with a recorded opening time, v2 records only); **Do people come back?**: a cohort grid (rows = the week a person was first seen, columns = weeks since,
cells = the people active again; a cohort of fewer than 5 is one hatched bar, a cell is protected as the partition returned / not returned, a percentage needs a cohort of 20, otherwise counts) and the week-1, week-4 and habit shares with the weeks-active histogram; **Recording health** as mini bars (glance against engaged, real errors, benign notifications, visits that dropped keys, time attributed to a section); then **How this is measured**. The page has no "What changed since last report" block: the signals S0 to S9 (observation, baseline, threshold, confidence, what each does not show) are still computed and are printed by the text report (`--text`, or without `--html`), which keeps that section and its Checked ledger unchanged. What the owner must see stays on the page: the stale-export warning and the duplicate, skipped and unknown-record warnings (banners at the top), the coverage ribbon, and the usual range and change of every key figure.
Every chart is one `role="img"` with a label that holds its numbers (a withheld number is `<5 users` there too) and has a one-line caption and a **Show data** disclosure with the table equivalent (every number of the previous version of the page is in these tables); the charts are HTML and CSS with a little inline SVG, so their text stays real text and readable at 390 px. A chart is never drawn from a group that is withheld: a stacked bar shows the printed groups
only, as shares of the printed groups, so its length can never reveal a withheld group by subtraction. The weekly series behind the sparklines and the changes (engaged visits per person, median minutes, glance share) are derived from the same model with the same guards and are only compared over weeks recorded under the same rules.
Weeks run Sunday to Saturday and are complete once Saturday has passed; only completed weeks are compared; the first week of data (when the data starts mid-week) is provisional. Every breakdown that rests on fewer than 5 distinct people prints `<5 users`, a figure that would reveal such a group by subtraction is withheld too, and a percentage prints only with a denominator of 20 or more.
**This week so far against the same days last week** (under the weekly people chart, and after the weekly lines in the text report; `week_to_date`, key `wtd` of `aggregate`): the week in progress is not comparable with a completed week, so this block compares like with like. The current window is the Sunday to the day of the data (that day is still in progress); the previous window is the same weekdays of the week before (on a Wednesday: Sunday to Wednesday of both weeks). It shows the people active and the visits (all sessions, glance visits included, v1 and v2 alike) of each window and the difference with its sign, as facts with no verdict word. The guards are the weekly figures' own: a group of fewer than 5 people prints `<5 users` and then no difference is shown, and a percentage is added only when the previous figure reaches the percentage minimum (20; `--show-all` lowers it to 1). When the data starts after the previous window starts, the block says from which day; when nobody visited in the previous window it says there is not enough data; on a Sunday with nothing recorded yet it says so; and when the two windows were recorded under different rules, it notes that the visits are not comparable.
The wording blocklist (who, top users, least active, engaged people, people who read X, a stated reason for a change) is enforced by a test. `tests/test_usage_report.py` checks the text equivalents, the guards inside the charts (including a property test over the drawn values) and 7 seeded defects of the chart rendering, the week-so-far block (hand-computed windows and 5 seeded defects); `tests/dashboard_browser/usage_page_check.py` checks the page in Chrome at 1400 and 390 px.

## Adding to it
Projects and releases are the `PROJECTS` / `RELEASES` lists at the top of `build_dashboard.py`;
`CURRENT_RELEASE` and `PROVISIONAL` set the default release and which releases are marked provisional.
**A project added to `PROJECTS` needs a full build** (`python3 program_dashboard/build_dashboard.py`, no flag): the epics, their changelogs (cycle time, release join dates) and the release windows are read only by the full pull, and the `--add-*` flags re-read the other sections only for the epics already in `build/program_data.json`, which holds none of the new project's. After the full build every section, filter chip, chart and link follows the list by itself (the page iterates `DATA.projects`); the project's pod labels use the plain `pod` pattern unless `release_planning/config_<project>.json` exists.
**A project key that is a reserved JQL word** (`INT`: Jira answers "'INT' is a reserved JQL word. You must surround it in quotation marks") is listed in `JQL_RESERVED_KEYS` in `build_dashboard.py`, which `definitions()` writes into the payload (`DATA.defs.jqlReservedKeys`; the page keeps an equal fallback literal). Every query that names a project key goes through `pkey` / `pkeys` (the collector) or `pkey` / `pkeys` (the page): a reserved key is quoted, every other key is left as it is, so the other projects' queries are unchanged. `tests/test_program_dashboard.py` scans both sources and fails on a project key interpolated without the helper; the browser suites check that every link and every Refresh query quotes `"INT"`.
Reuses `dashboards/edct_from_jira.py` for the Jira client and EDCT. The output contains epic titles and
internal figures: `program_dashboard/build/` is git-ignored, never commit it.

## Quality gates and safety
- **One definitions source.** `definitions()` in `build_dashboard.py` writes the shared rules (closed bug statuses, NFR label and categories, commitment types, target scope) into the payload as `DATA.defs`; the page reads them from there and keeps its own literals only as a fallback for an older payload. `tests/test_definitions_contract.py` keeps those literals equal to the collector's, checks that the page and collector agree on `SCHEMA` / `PAGE_SCHEMA`, and that every Jira field id the page queries is known to the collector. Change a definition in `build_dashboard.py`, then update the fallback literal the test names.
- **Payload checks.** A build stops when required data is missing (`validate_payload`); missing optional sections are warned about. The page shows a notice when the data layout number differs from the one it expects. The tooltip of the header stamp names the commit the page was built from and whether the working tree had uncommitted changes.
- **Safe writes.** `build/program_data.json` is written through a temporary file and the previous file is kept as `program_data.json.prev`. Only one mode flag may be given per run (`--add-bugs --add-capitalization` is an error, run them one after another). Links and bugs carry their own pull times (`linksPulledAt`, `bugsPulledAt`).
- **Refresh safety.** Each Jira call has a 60-second deadline (one retry); a page that says "more" without a way to continue, or repeats a page, stops the refresh and applies nothing; each window of the main read (epics and bugs) is checked against Jira's own count (`searchResultMode: count`): a shortfall is read once more, and more than 3 missing issues stops the refresh with nothing applied (a connector answer without a count skips the check); the Capabilities step reads everything before it changes anything; a link whose query holds `NaN` or `undefined` is dropped instead of opening a wrong list. In the automatic attempt the note names the real reason unless it is an access problem.
- **Leak scan.** `python3 program_dashboard/leak_scan.py` (add `--staged` for a pre-commit hook) learns the real issue keys, epic titles, people and team names from the local `build/program_data.json` and fails when any appears in a tracked file; it prints only file and line. Run it before every commit. The CFB reporter account id can be supplied through `CFB_REPORTER_ID` instead of the tracked `release_closure/config_pmn.json`.
  The same run ends with a **report-only** overview of the rest of the repository (`config/`, `release_closure/`, `dashboards/`, `release_planning/`): counts per file of account ids, cloud ids, the tenant host and team names. It never fails the run; it shows what a public repository exposes outside the dashboard, for the owner's decision (moving them to secrets, making the repository private).
- **Fallback.** Before this work the published page was Version 52. `build/fallback_v52/` (git-ignored) holds the template, builder, README, data and the page itself with `RESTORE.md` to put them back.
