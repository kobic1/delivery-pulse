# Delivery Pulse

One filterable page across projects and teams (PMN, CXCO, CXSUP, CXWFM, WFM, CXINT): the release status in the
shape of the weekly release status email, plus bugs, customer-found bugs (CFB), epic dependencies and a capability
view. Every issue count links to the matching Jira issues, and every chart mark has hover text and a Jira link.

Layout, top to bottom: five headline tiles (Epics Delivered, Forecast Epics, EDCT Days, Open Bugs, Epics by AI,
each with a plain-fact line and a kicker saying whether it is release, month-to-date or today), a collapsible
**Needs Attention** panel, then **Delivery** (burnup), **Efficiency** (EDCT against the 10-day target) and
**AI Adoption** (share of epics built by AI agents) with a Week / Month / Quarter switch, **Quality** (open bugs
trend, customer-found bugs), **Dependencies** (open dependencies between epics on a board with a column per sprint), a separate **CXCROSS** section (status per project for each CXCROSS Capability, and which projects are behind), an **NFRs** section ("NFR Epics (Label or Category)", five tabs), a **Capabilities** section, then a separate **Delivery Cycle Governance** section (the pods of a program per delivery cycle; see below) and, last, "Release Analysis": trend by release, Done Capabilities per release, by project, by team
and data quality. A quiet floating "Back to Top" button appears when you scroll up after reading well down the page (it stays hidden if the page cannot scroll). The header shows "Data as of ..." with a Refresh button and, compactly, the read time of each section with its own pull (Capabilities, the Open CFB Root Cause Analysis state). Monthly figures use the email's rules:
resolution month, AI-implemented epics for EDCT (Maintenance-category epics left out; the AI figures also leave out SOW).

```bash
set -a && source .env && set +a
python3 program_dashboard/build_dashboard.py              # read Jira (a few minutes) and render
python3 program_dashboard/build_dashboard.py --reuse      # re-render from the last pull, no Jira calls
python3 program_dashboard/build_dashboard.py --add-deps   # add dependency links (any issue type at the far end, plus story-level links under the release epics) and capabilities to the last pull (no changelog calls), then render
python3 program_dashboard/build_dashboard.py --add-planning  # also add due dates, target sprints, the sprint calendar, status-since dates, bug updates, assignees, the Flagged field and the bugs under each epic
python3 program_dashboard/build_dashboard.py --add-hier      # add the CXCROSS Initiative > Capability hierarchy
python3 program_dashboard/build_dashboard.py --add-nfr       # flag the epics that carry the label NFR (the Issue Category is already in the data)
python3 program_dashboard/build_dashboard.py --add-bugs         # re-read the bugs (customer-found: reporter OR Salesforce case, Closed dates), the update dates and the Open CFB state, then render
python3 program_dashboard/build_dashboard.py --add-cfb-open     # root cause analysis state of the customer-found bugs (Open CFBs table), 4 requests
python3 program_dashboard/build_dashboard.py --add-capabilities # the Capability list and ALL their child epics, any project (Capabilities section, Done Capabilities per Release); a few minutes
python3 program_dashboard/build_dashboard.py --add-pods      # the pod labels of the epics (Delivery Cycle Governance, Group By Pod); a full build and --add-planning include them
python3 program_dashboard/build_dashboard.py --add-cycles    # optional: the pod grouping of Delivery Cycle Governance (needs cycles.config.json, see below), then render
# The Atlassian site id for Refresh is read from the site (or from JIRA_CLOUD_ID); it is not stored in the repository.
```

Writes two files to `program_dashboard/build/` (git-ignored, they contain epic titles):

- `Delivery Pulse.html`: a single self-contained file (inline JS and SVG, no external libraries; the only external
  request is the Be Vietnam Pro font stylesheet, with Arial as fallback). Open it in a browser. Nothing is sent
  or published. The Refresh button there only explains that it needs the published page.
- `Delivery Pulse (artifact).html`: the same page as a fragment for the Artifact tool. Publish it with the `mcp`
  capability declared for the Atlassian connector and the single tool `searchJiraIssuesUsingJql`:
  `{"mcp": {"servers": [{"server": "Atlassian", "tools": ["searchJiraIssuesUsingJql"]}]}}`.

## Time base
Every timestamp on the page is shown in Israel time (labelled), and the as-of day used for ages, sprints and SLAs is the
Israel-local date of the snapshot or of the last Refresh, whatever the viewer's timezone.

## Snapshot, and Refresh in the published page
Jira is read once at build time and baked into the file; the build time is shown at the top. The pull is slow
because cycle time needs one changelog request per Done epic and the burnup needs one per epic (about 3,000).

In the published artifact, **Refresh from Jira** asks the viewer's own claude.ai Atlassian connector for what
changed since the snapshot (`updated >=` the day before) and merges it in: new, moved, Removed and Done epics,
new and fixed bugs, accessibility flags. The first click asks the viewer for Jira access. Failures say what to do
(not allowed, connector not connected, expired sign-in) and leave the data on screen unchanged.
Refresh **merges** into the existing record, it never rebuilds one from the response: it reads the planning facts too (due date,
Target Sprint, assignee, parent Capability, Flagged, last update, NFR label) with the collector's names and normalisation, overwrites only
what the response carries, and leaves every other field as it was (cycle time, sprint calendar, status-since, Closed and Ready to Deploy
days and the Salesforce-case and reporter flags of a bug are kept). A field comes back empty (null) only when the response includes it as
empty; a field the response does not include is never cleared. A due date removed in Jira therefore clears only if Jira returns the field.
A status change drops the status-since day of the old status, and a reopened epic drops its cycle time; both are filled in at the next build.
**Refresh does not update** dependency links, story-level links, capabilities, bugs under epics or cycles pods (the result message says so):
those need a rebuild (`--add-deps`, `--add-capabilities`, `--add-planning`, `--add-cycles`), as do cycle time and release join dates for
newly changed epics. Refresh is for the numbers moving, not a replacement for the build.

## Filters
Release (bare numbers; a release that is running gets an "In Progress" chip), Projects (with an All Projects
option), Teams (searchable multi-select) and Commitment Type (**all three types by default**). Reset Filters counts
every changed control. Section-level controls: Week / Month / Quarter for the EDCT and AI charts, Priority, CFB
Yes/No and an accessibility toggle for the Bugs Backlog, and Version / Month / Quarter for the CFB chart and table.

In a file the filter state is kept in the URL hash, so a view can be shared as a link, e.g.
`#r=26.4&p=PMN&t=Ascenders&c=Committed|Not%20Set`: `r` release, `p` projects, `t` teams, `c` commitment types
(omitted when all three), `ax=1` include accessibility bugs, `bp` bug priorities, `cfb=yes|no`, `g=week|quarter`
(EDCT and AI period), `cg=month|quarter` (CFB grouping), `dp=epics|overdue|external|unplanned` (dependency board quick filter), `cx=committed|notset|stretch` (CXCROSS Commitment Type radio, All by default), `nt` (NFR tab); an empty Projects or Commitment Type selection is stored as `p=none` / `c=none`. In the published page the filters are remembered in the
viewer's browser instead. A section whose filters leave nothing to show says why.

## Definitions
Taken from the Program Intelligence Agent (`.claude/agents/program-intelligence-agent.md` and
`program_intelligence/definitions/*.yaml` on branch `claude/zealous-cannon-ls64p7`). They are restated in
`build_dashboard.py` and the template, so this tool does not need that branch at run time.

- **Removed is excluded from every figure.** Done means the status named Done, never Jira's Done category.
- **Scope is Fix Version plus Commitment Type** (customfield_10094). Status never defines scope.
- **The scope target never changes with the Commitment Type filter**: it is always Committed or no Commitment
  Type, with Stretch left out. **Forecast Epics is the target scope on the first day of W1** (the epics that were
  in the release on that day and still are); the burnup's scope label, point, tooltip, subtitle and caption and the
  even-pace reference read the same single value, and the tile adds how many were added since (and today's count,
  as a link). Before W1 it shows the target so far. The links use `fixVersion WAS "<release>" ON "<W1 date>"`.
  The Epics Delivered tile follows the Commitment Type filter and says so; its fact line gives the target-type
  delivered figure against the W1 scope.
- **Epics by AI** counts Done epics resolved in the month, **leaving out the Issue Categories Maintenance and SOW** (see the next paragraph), that carry a release fix version from the first to the last listed release (the Jira links carry the same filter, so they open what is counted); the tile also shows the epics **not marked as AI** as its own link: the field is a multi-select, so "not Yes" is `(cf[15229] is EMPTY OR (cf[15229] = No AND cf[15229] != Yes))` (an epic ticked both Yes and No counts as AI); Yes plus not-AI always equals the resolved count. Never `!= Yes` alone: it drops the empty ones. In the AI Adoption chart every bar opens the epics of its period (the bar's own population) that are **not** marked as AI; the hover text says so ("2026-09: 85% marked as AI (242 of 284). Click opens the 42 epics not marked as AI"), and the View Data table links the resolved, marked and not-marked counts of each period.
  **AI exclusion (Maintenance and SOW).** Epics whose Issue Category (Jira field cf10139, stored spelling, compared without regard to case) is Maintenance or SOW are left out of **every AI figure**: the Epics by AI tile and its previous-month line, the AI Adoption chart for Week, Month and Quarter, its View Data table, the Release Analysis AI share (the Epics by AI tile for the release, the AI chart per release and the Epics by AI column of its table) and all their Jira links, which carry `(cf[10139] is EMPTY OR cf[10139] not in (Maintenance, SOW))` next to the same resolved-in-period and fix-version population as the denominator. One constant in the page (`AI_EXCLUDED_CATEGORIES`) drives both the numbers and every link. It is shown, not hidden: the tile and the section subtitle say "Maintenance and SOW epics are excluded from every AI figure" with the number of epics left out in the displayed period or population as a link (`cf[10139] in (Maintenance, SOW)`, same basis); the AI View Data table has an "Excluded (Maintenance, SOW)" column per period with links, the release table has the same per release, and "How This Is Calculated" explains why. **EDCT is not an AI figure** and keeps its own rule (Maintenance only, as the weekly email counts it); its values and links are unchanged. The URL state of the tile does not change.
- **Cycle time** is EDCT only: calendar days an epic ended in In Progress or Validation, flagged days excluded.
  Identical to `dashboards/edct_from_jira.py`; the build checks every epic against it and reports differences. Trend by Release shows P50 and **P90** (linear interpolation) for releases with 5 or more Done epics.
- **Burnup** (selected release): only the 12 delivery weeks W1 to W12, from the first day of the second week of
  the Jira release window (the IP week is not drawn) to the release date. Scope is one number, the target-type
  epics in the release on the first day of W1. Done is the target-type epics closed, cumulative by resolution
  date, with earlier closures counted at the start and later ones on the last day. The dashed line is an even pace
  from zero to that scope, a reference and not a forecast. A dotted marker and a fact line under the chart present the first six weeks (W1 to W6, ending on W1 start + 41 days) as **Delivery Cycle 1**: the number of **Committed** epics planned in it (strictly Commitment Type Committed, Not Set excluded), out of all Committed epics in the release, Done and not Done, and those with no due date or Target Sprint. An epic is planned in the cycle when its Target Sprint (counted by its end date, so the 2nd sprint of the release or earlier) or its due date is on or before the cycle end; **with both, the later one counts**, otherwise the one that exists. The dependency board keeps the due date over the Target Sprint. The Jira links reproduce the same set. **The count is printed on the chart**, left of the dotted marker at the top of the plot: "Delivery Cycle 1 · N epics planned" with "N Done" under it (the same N and Done as the fact line below, always in sync; the label wraps to three or five short lines when the space left of the marker is narrow, so it never touches the axis or the other chart labels). A dot on the marker sits at N on the chart's own epic scale (a fact about the plan, not a forecast). The label and the dot are one link that opens the planned epics in Jira, with hover text and keyboard focus. View Data adds two columns, Delivery Cycle 1 Planned and Delivery Cycle 1 Done, filled on the row of the cycle end (W6). Release windows come from the Jira versions.
- **Bugs backlog** (selected projects and teams; release and commitment filters do not apply): created, resolved
  and open per week for 26 weeks, Monday-aligned. **A bug is open while its status is not Done, Ready for Deploy, Closed, Resolved or Removed** (for bugs, Ready for Deploy counts as Done; epics keep Done = the status named Done)
  (the status rule of the alert rules; resolution is not used, so Validation counts as open). Open at a
  week end = created before it and (open by status now, or closed with a resolution date on or after it). A bug closed by
  status with no resolution date has no dated evidence of ever being open and is left out of the weekly line, with a note and
  a Jira link in the section's About text. The priority control offers P1 to P4; open bugs with no P1 to P4 priority stay in
  the table's Total and are named under it with a link. Accessibility bugs
  (`summary ~ "[Accessibility]*"` or label `DWP_Accessibility_Defect`) are excluded unless switched on. Its own
  Priority and CFB filters apply to this section only and the Jira links carry them.
- **Open CFBs** (the first block of Customer-Found Bugs; the five fixed-CFB tiles that used to head the section are gone, the chart and table of fixed CFBs and regressions follow it): a strip (Open CFBs, RCA Not Done with RCA Done and Not Required, Over SLA, Regression Yes, all linked) and a **collapsed** list ("Show Open CFBs (N)", a details disclosure that stays open while the page re-renders, for the visit only). The RCA column sits next to Status and Priority; an RCA text row opens under its bug and never scrolls the table. The table fits 1280 to 1440 px and says "Scrolls sideways" whenever it overflows. Contents: every bug reported by the CFB account in the selected projects and teams whose status is not Done, Ready for Deploy, Closed, Resolved or Removed. Columns: key, summary, project, status, priority, age (whole calendar days to the as-of day), SLA days (P1 3; P2 7 with a regression, 14 without; P3 and P4 7 with, 30 without; none without a P1 to P4 priority), SLA due date (created plus SLA days), required against actual, regression, incidents (Number of Incidents, plus linked Problem/Incident issues), and the Root Cause Analysis state. **RCA Done** = the Root Cause Analysis field was edited (differs from the unedited template) or the RCA Review Status is Approved; **Not Required** = review status Not Required; **RCA Not Done** = empty or still the template. The field is pre-filled in Jira, so non-empty proves nothing and Jira cannot search for it: at build time the template is recognised as the text shared by five or more CFBs (only a flag is stored, and an excerpt of an edited text for open bugs). A template variant used by fewer than five bugs reads as edited. It follows the Projects and Teams filters, like the chart, not the bug section's Priority, CFB or accessibility controls; a note gives the open count across all Jira projects.
- **CFB (customer-found bug)** everywhere on the page (the Customer-Found Bugs section, Open CFBs, the Needs Attention production-bug rules, the "Open CFB Now" counts, the bug section's CFB filter and every Jira link): a Bug **reported by the CFB account (`release_closure/config_pmn.json`) OR linked to a Salesforce case** (the field SF Connection Case Reference, customfield 10329, is not empty); the Jira links use `(reporter = "<account>" OR cf[10329] is not EMPTY)`. **This is broader than the alerting rules** (`config/rules.yaml`, the Teams alerts), which are not changed and use the reporter only. Open still means a status other than Done, Ready for Deploy, Closed, Resolved or Removed. The fixed chart and table count Bugs with status Done or Ready for Deploy (Ready for Deploy counts as Done for bugs; its resolution is Fixed, and one with none still counts) and resolution Fixed or Fixed - Config **by their Closed date** (the Jira field Closed, customfield 10099, taken as the Israel-local day), not by the resolution date; the Jira links use `cf[10099]`, and a fixed CFB with no Closed date uses its Ready to Deploy Date (customfield 10051; Ready for Deploy bugs) and then its resolution date (the section's About text counts both fallbacks, with links). The Open Bugs trend and the Open CFBs table do not use the Closed date. Version = the release windows; Month = the last 12 calendar months (its total row says "Last 12 Months"); Quarter = calendar quarters since the data starts. Regressions use the Regression field; PQCR Cases sums Number of Incidents. A line in the About text counts the CFBs that carry a Salesforce case although another person reported them. The bugs are read with `--add-bugs` (a full build includes it).
- **Dependencies** (open ones only): an explicit Jira link of type "Dependency" (outward "depends on") or "Blocks"
  where both ends are epics by default, or at least one end is an epic and the other end any issue type (Initiative, Capability, Story, Task and so
  on; a card shows the provider's issue type) under All, normalised to a dependent and a provider. **Epics Only is the default view and every figure counts the pairs between epics** (the headline reads, for example, "12 open dependencies between epics"); the quick filter **All** (hash `dp=all`; `dp` is omitted for the default) adds the links to other issue types, which the headline mentions as a secondary line ("9 including links to Capabilities, Initiatives, Stories"). Needs Attention counts the epics-only set. Dependency and Blocks links on stories, tasks and bugs UNDER the release's epics (not test items, not pairs already counted) are a separate fact line with a link, not on the board and not in the figures. Only pairs where neither end is Done are
  shown (complete pairs are counted and left out). The board has one column per sprint plus "Not Planned", one card
  per provider epic. The **planned sprint** of the provider is the sprint containing its due date (the due date is
  stronger), otherwise its Target Sprint; when both exist and disagree the card, the hover and the View Data table
  show both ("Due 2026-09-04 (Sprint 195) overrides Target Sprint 199 (2026-11-25)"). A due date outside the sprint
  calendar, or a Target Sprint the calendar does not know, is said so, never silently replaced. Sprint windows come
  from the Target Sprint labels (the label date is the start, sprints run three weeks). The key on a card opens that
  ticket (`/browse/KEY`); a small "Open with Dependents" link opens the provider with the epics it blocks. A pair
  linked both as Dependency and as Blocks counts once. **Overdue** = the planned sprint has ended and the provider is not Done.
  **External** = the provider is in a different Jira project. Hovering a card lists the epics it blocks. Other link
  types do not count, links to Removed issues are left out, and a link means a dependency is recorded, not that it
  is risky (no link is not no dependency). Counts only; no aging logic beyond overdue. 
- **Needs Attention** (computed live from the data the page holds; thresholds in one `CFG` object in the template):
  production bugs (customer-found, status not Done, Ready for Deploy, Closed, Resolved or Removed: the same rule as the Open CFBs table) out of SLA or due soon
  (age in whole calendar days from creation; SLA days: P1 3; P2 7 with a regression, 14 without; P3 and P4 7 with, 30
  without; due soon from 70% of the SLA; no priority means no SLA), production bugs with no update for 3 days,
  overdue dependencies, epics in Validation for more than 3 business days (Friday and Saturday and the Israeli public
  holidays are not counted; the holiday list, 2025-06 to 2027-12 in python-holidays style, is in the thresholds object
  and Chol HaMoed is not excluded; the panel says when the as-of date is past the list), open external dependencies and
  a hygiene group. The 42-day In Progress group was dropped. One row per Jira item, never ranked by team or person, and the
  panel states what it could not see (comments, story data, anything older than the snapshot).
- **Capabilities** (own section, nav link "Capabilities"): two tables. *Capability Status Summary*: the Capabilities of the six projects (project of the Capability) whose **Fix Version is the selected release** (the owner's assumption that the Capability's fix version is its required release), Removed excluded, by status (New, In Definition, Ready for Dev, In Progress, Done, plus Other Status only when non-zero) with totals; every number links to Jira. *Child Epics of These Capabilities*: ALL non-Removed child epics of those Capabilities in any project and with any fix version, by the project of the epic (the six first, then other projects alphabetically) and status, with % Done from 5 epics. Both follow the Release and Projects filters; Teams and Commitment Type do not apply. Needs the `--add-capabilities` pull. A line under them counts the epics in scope with no Capability parent, with the exemption below.
- **Capability parent hygiene exemption**: an epic whose Issue Category is one of R&D - 3rd party upgrades, R&D - Arch/infra refactoring, R&D Infra, R&D - Low env. cost optimization or Maintenance (compared without regard to case; "NFR" as a category is not exempt) is not flagged for a missing Capability parent in Needs Attention, the Capabilities section or the NFR data gaps; each place says how many were exempted, with a link. The Jira link uses `parent is EMPTY AND (cf[10139] is EMPTY OR cf[10139] not in (...))`.
- **Epics per Release** (Release Analysis, Trend by Release): each bar is the **higher of the target scope and the target epics Done**, so the scope on top of the page and the chart agree. Target scope is the Forecast Epics tile's number (Committed + Not Set epics that were in the release on the first day of W1, the target so far before W1; the Projects and Teams filters apply, the Commitment Type filter does not); Done is the target epics (Committed + Not Set) with status Done, the burnup's Done. The light bar and its label show the higher value, the dark bar is Done; the hover text gives scope, done and which one the bar uses ("Bar shows the higher of scope (401) and done (737): 737"), and says how far Done is above scope when it is (epics added after W1 count in Done). The light bar links to the set it counts (the scope link uses `fixVersion WAS ... ON <W1 date>` like the Forecast tile, or the Done epics when Done is higher) and the dark bar to the target Done epics. The View Data table lists Target Scope, Target Done, the bar value and, as before, the epics and Done of the selected Commitment Types. The other per-release figures stay on the epics of the selected Commitment Types and say so: Cycle Time per Release (Done epics), Epics by AI (Done epics after the Maintenance and SOW exclusion) and the By Project and By Team tables.
- **Done Capabilities per Release** (Release Analysis): the fourth chart of the Trend by Release grid, on a second row beside the three epic charts (the same card size and style; three across at 1100 px and wider, one column below), its View Data table under the Trend by Release table; the chart is in the form of the epic charts: one bar per release from the second listed one, the light bar all Capabilities with that fix version, the dark part the Done ones (status named Done), the label "done/total" on top, hover text and Jira links, a dashed outline and an asterisk for running releases, and the by-project split (the six projects, and Other for CXCROSS and other projects whose Capabilities parent these projects' epics) in the hover text and the View Data table. A Capability with several fix versions counts under each, one with none is in a footer line. Not affected by the filters.
- **NFR share**: the NFR Epics in Scope tile keeps its headline count (every NFR epic under the page filters, printed with its own denominator: all epics under those filters). The percentage under it is taken of the **target scope**, the same set and the same number as the Forecast Epics tile (Committed + Not Set epics that were in the release on the first day of W1, the target so far before W1, under the Projects and Teams filters; the Commitment Type checkboxes do not change it): "N% of D target-scope epics are NFR (X of D)", where X counts the NFR epics (label NFR or an NFR Issue Category) in that set and links to Jira on the same `fixVersion WAS ... ON ...` basis as the Forecast Epics link. A share is shown only when D is 5 or more; D always equals the Forecast Epics tile.
- **CXCROSS** (separate section): epics of the six projects whose parent Capability lives in project CXCROSS, for the
  selected release, the Projects and Teams filters and **its own Commitment Type radio** (All, Committed, Not Set, Stretch; it replaces the checkboxes for this section only). A Capability row is listed when at least one of its epics has the chosen type and its cells count only those epics; Behind cells are recomputed over them. One row per CXCROSS Capability (its Initiative as a muted subtitle), one
  column per project in the standard order, each cell showing done/total linked to Jira. A cell is **Behind Capability
  Fix Version** when an open epic of that project is planned later than the Capability (its earliest release version is
  later than the Capability's latest) or is not Done although the Capability's latest release-named fix version has
  ended. The Capability's Fix Version is taken to be the program's **Required Fix Version** (an owner assumption, not
  independently verified), shown as "Required Fix Version" and "Behind Required Fix Version". Facts only: no at-risk verdict, no due dates, no owners; rows and columns
  are never ordered by lateness. Only CXCROSS Capabilities that have epics under the six projects are counted; CXCROSS-owned epics are not included.
- **NFRs** ("NFR Epics (Label or Category)"): an epic is an NFR epic when it carries the label `NFR` (exact spelling) or
  its Issue Category (field 10139) is one of four values listed in `NFR_CATEGORIES` in the template. Both are
  self-reported in Jira, and the section says how each epic matched (label only, category only, both). It follows
  every global filter, excludes Removed and CXCROSS-owned epics, and prints its denominator. Five figures stay above
  five tabs (By Project, By Category, By Commitment, By Capability, By Team); the tab is kept in the URL as `nt=`
  (default By Project; Reset returns to it). Status classes are Not Started (including In Definition), In Progress,
  Validation and Done, with an Other Status column when a status fits none. No verdicts, rings or rankings.
- **Delivery Cycle Governance** (after NFRs and before Release Analysis, which stays last; nav link "Cycles"): a view of the dashboard's own epics, **not a separate pull and not configured**. It follows the Release, Projects, Teams and Commitment Type filters (one line under the heading says so), so selecting one project shows that project's epics. **Delivery Cycle 1** runs from the Jira release start to the end of W6 (release start + 48 days, the same boundary as the Epic Delivery chart's marker) and **Delivery Cycle 2** from the next day to the release end; the cycle containing the as-of day is the default (before the release: Cycle 1, after it: Cycle 2). An epic belongs to the cycle that holds its **planned date**: the later of its due date and the end of its Target Sprint when it has both, otherwise the one it has (an epic with neither is not planned). Facts only: no verdict, no colour for a group, no ranking, no share under 5 items. Groups are the **Epic Teams** of the selected epics in alphabetical order (an epic listing several teams counts under each; the total row counts it once; epics with none are under No Team). The headline strip (Planned, Done, Due So Far with "N of M due epics done", Overdue, Due Next 7 Days, Stale, Open Bugs, Flagged, Carry-Over, No Planned Date) sits on the Overview tab (a team tab has its own compact strip of six); the tabs wrap onto rows so all stay visible: Overview (one row per team), one tab per team (epics with flags, weekly plan against actual with weeks counted from the cycle start date, the planned epics, carry-over, active epics with no planned date, bugs under each epic) and Capabilities (the parent Capability of each epic in view with the status of all its child epics). Rules: Planned = epic (Removed excluded) with its planned date in the cycle; Done = status Done; Due so far = planned and before the as-of day (Israel date of the snapshot); Overdue = before it and not Done; Stale = more than 30 days overdue (planned and carry-over together); Due next 7 days = planned today through today plus 7, not Done; Carry-over = not Done with a planned date before the cycle start, shown only once the cycle has started; Flagged = the Jira Flagged field; bugs = type Bug whose parent is the epic, open = status not Done, Ready for Deploy, Closed, Resolved or Removed (a read of Jira found no other relation between a bug and an epic); EDCT is the dashboard's, read for Done epics. Every number links to Jira by the page's filters plus the exact epic keys. URL keys: `cy` (`DC1` or `DC2`; omitted for the default), `ct` (`overview`, `caps` or a **slug of the team's name**), `cgb=pod`, `cp`, `cs`, `cc`, `cf`; invalid values are ignored and the search text is never put in the address. The data it needs beyond the main pull (assignee, Flagged, and the bugs under each epic) comes from the planning pull (`--add-planning`); without it those cards say so instead of showing a number.
  *Pods from labels (Group By Pod).* **Group By: Team | Pod | Pod Group.** Pod groups the epics by their Jira pod labels, from the dashboard's own epic data for all six projects, with the rule of the release planning report (`release_planning/model.py`, `pod_labels`): an epic's labels are tested without regard to case against the project's `pod_label_regex` (read at build time from `release_planning/config_<project>.json` and stored in the data as `podRx`; a project without a configuration uses the plain pattern `pod`, the text anywhere in the label; CXCO also accepts a label of the form `CXCO-Name-1` but not `CXCO-12345`). Only the matched labels are stored on the epic (`pl`), by `--add-pods`, `--add-planning` or a full build; Refresh applies the same pattern in the page to the labels it reads (absent stays, empty clears). An epic with several pod labels counts under each pod once; an epic with none is under **No Pod Label**, the last group. Pods are grouped without regard to case and shown with the first spelling found; links list every spelling (`labels in (...)`, and the hover text says when spellings are combined). The Overview has one row per pod in alphabetical order, never ranked: Teams (what the Epic Team field of the pod's epics holds; a pod is not forced into one team), Projects, Epics in Release (linked by label, every cycle), Planned, Done, Due So Far, Due Epics Done, Overdue and Due Next 7 Days. A group view is the same as a team's. With more than 12 pods a searchable selector replaces the tabs. A line under the section heading says "N of M epics have a pod label" with links. Pods follow the Release, Projects, Teams and Commitment Type filters and the cycle. The address uses `cgb=label` (`cgb=pod` stays the optional pods pull, shown as Pod Group only when that is configured); the default is Team. Known limits, printed in How This Is Calculated with the count of distinct pod labels per project and a link: a pod whose label does not contain the pattern text is not detected, a typo that contains it counts, and a label that contains the text but is not a pod cannot be told apart.
  *Optional pod grouping.* The **Pod Group** option of the Group By switch appears only when the optional pods pull exists and the selection includes one of its projects. The pods pull (`cycles.py`, `--add-cycles`) reads the pod groups, group leaders and the label-to-pod map from a Confluence pods page (`/wiki/rest/api/content/<id>?expand=body.storage`, same credentials as Jira; the table is found by its row headers and validated, with the last good read as a visible fallback) and the projects of the configured scope; its configuration (page id, Epic Team names, scope dates) lives in a git-ignored `program_dashboard/cycles.config.json` (or the path in `CYCLES_CONFIG`); only `cycles.config.example.json`, with fictitious values, is committed. In Pod mode the same section lists those projects' epics grouped by pod (the others under No Pod Assigned). A build without the file produces the whole section from the raw data alone. Tests use synthetic fixtures (`tests/test_program_dashboard_cycles.py` for the pods pull).
- **Scroll anchoring:** when a filter changes and sections re-render, the block the reader is looking at is kept at the
  same screen position (a control the reader just used is held instead of the centre block). Open details panels
  stay open.
- **Tables and tabs:** every sideways-scrolling table is a labelled keyboard stop (`role="region"`, `tabindex=0`) and says "Scrolls sideways" whenever it overflows; the Cycles and NFR tab bars wrap onto rows, so every tab is visible and the arrow, Home and End keys never focus an off-screen tab; the flags table becomes cards on narrow screens. A control in a non-sticky filter bar (narrow screens) or inside a section is held in place when pressed; a control in the sticky bar leaves the block in the middle of the screen where it is. A tooltip closed with Esc opens again on the next focus or hover. Reset Filters also closes the expanded bug rows.
- **Guardrails:** no percentile, share or trend on fewer than 5 items (including the bug direction facts);
  running releases are provisional; epics listing several teams count under each team (the total row counts them once).
- **No ranking or scoring of any team or person.** Teams and capabilities are listed alphabetically and the views
  report scope and status, not performance (`rules/no-employee-evaluation.md`).
